## 1. コンセプト

いま持っているイヤホン(AirPodsでも数千円のワイヤレスイヤホンでもいい)を買い替えずに、翻訳機と議事録機に変える。

**イヤホンは音の入出力口のままにして、認識・翻訳・要約・記録という頭脳は全部スマホ側に置く。** この分離により「イヤホンを機能拡張する」が「スマホ側にモジュールを足す」に変換される。ハードウェアを増やさずに機能だけ増える構造が核心。

翻訳アプリでも議事録アプリでもなく、**耳の機能拡張プラットフォーム**を作る。翻訳と議事録は最初に載せた2つのモジュールであって、ゴールではない。

### 守るべき設計判断

引き継ぎ後に壊してほしくない判断を、理由つきで挙げる。

| 判断 | 理由 |
| --- | --- |
| 音声認識と読み上げはブラウザ内蔵機能を使う | 従量課金の本体は音声認識。ここを端末側で処理することで、APIに渡すのがテキストだけになりコストが1〜2桁下がる |
| モジュールは共通インターフェースだけを守る | 機能追加のたびに画面もマイク制御も作り直す構造にしない。使う人が新しい画面を覚え直さずに済む |
| 議事録は文字起こし中にAPIを呼ばない | 会議が長くなっても課金が増えない。増えるのは停止時の1回だけ |
| モードを同時に2つ動かさない | 処理負荷とエコー干渉を避けるため |
| データは端末内が既定 | サーバーに会話を残さない。結果としてログイン機能が不要になっている(§8参照) |

## 2. 現在の状態

### 動くもの

| モジュール | 動作 | APIを呼ぶ回数 |
| --- | --- | --- |
| 翻訳 | 相手の発話を訳してイヤホンに読み上げ。向きはワンタップで反転 | 1発話につき1回 |
| 議事録 | 連続文字起こし → 停止時に要約・決定事項・ToDo・保留事項 | 停止時に1回だけ |
| ウォッチワード | 決めた語が聞こえたら耳で知らせる | 0回(端末内で完結) |

ほかに、議事録を利用者自身の Google ドライブへ Markdown で書き出す機能がある(§7)。

### 検証済み

音声認識をフェイクに、Claude API と Google Drive API をモックに差し替えて、ブラウザで全経路を通してある。

- 3モジュールの動作、モード切り替え、同意パネル、要約表示、localStorage保存
- ドライブ保存(認可 → フォルダ検索 → 作成 → アップロード → リンク保存)
- APIリクエストの中身(モデル、`output_config` の有無、`fallbacks` の有無、ストリーミング)
- ウォッチワードがAPIを1回も呼ばないこと
- `npm run build` / 新規ファイルの `npx eslint app/ear-hub app/api/ear-hub`
- ページエラーなし

### 未検証 — ここが引き継ぎの本題

**実機のイヤホンとマイクがある環境でしか確認できない。優先度順。**

1. **イヤホンのマイクで拾えるか** — 最大の未知数。ここが駄目なら企画全体が成立しない
2. **読み上げの回り込み** — 翻訳モードで、イヤホンから流れた訳文をマイクが拾い直して無限ループにならないか。読み上げ中は認識を `abort()` で落として音声を捨てる方式で回避しているが、実測していない
3. **iOS Safari の連続認識** — 認識が切れるたびに張り直す実装で対応しているが、実機での連続動作は未確認
4. **実際の Claude API 呼び出し** — 開発環境にキーが無かったため、モックまでしか通していない

### 確認手順

Preview URL をスマホで開く。先にイヤホンを Bluetooth 接続してからページを開くこと。iPhone はサイレントスイッチをオフに(オンだと読み上げが鳴らない)。

1. **ウォッチワード** — APIを使わないので、音声認識だけを切り分けられる。「開始」→ マイク許可 →「予算」と言う。画面に文字が出て、耳に「予算、と聞こえました」と返れば成功
2. **翻訳** — 英語で話しかける。初回はアクセスコードの入力欄が出るので、Vercel に設定した `EARHUB_ACCESS_CODE` を入れる。日本語の訳文が耳に返れば成功
3. **議事録** — 同意パネルを通して1〜2分喋り、停止。要約が出れば成功

1が駄目なら、イヤホンを外して本体マイクだけでも試す。それで動けばイヤホン側、動かなければブラウザの音声認識側。

## 4. アーキテクチャ

```
イヤホンのマイク
  ↓  Web Speech API(ブラウザ内蔵・無料)          speech.ts
確定した発話テキスト
  ↓  モジュールの onUtterance()                   modules.ts
  ↓  必要なときだけ POST /api/ear-hub             route.ts → Claude API
画面の字幕 / speechSynthesis で耳へ返す
```

### 発話1件の処理

1. `Listener` が確定した発話を `onFinal` で返す
2. `EarHub.tsx` が pending 状態のエントリを画面に積む(認識した生テキストをそのまま表示)
3. 順番が入れ替わらないよう、Promise チェーンで1件ずつ `onUtterance` を呼ぶ
4. 返ってきた `UtteranceOutput` でエントリを差し替える
5. `speak` があれば、**認識を落としてから**読み上げ、終わったら戻す

### エコー対策

読み上げ中に同じイヤホンのマイクが再生音を拾うと、訳文を訳し直す無限ループになる。`speakSafely()` で以下をしている。

1. `listener.suspend()` — 認識を `abort()` で落とす。`stop()` ではなく `abort()` なのは、途中の音声を確定させずに捨てるため
2. 読み上げ
3. 250ms 待つ(残響を拾い直さないため)
4. `listener.resume()`

信号処理はしていない。実機で不十分なら、待ち時間の調整か、`getUserMedia` の `echoCancellation` 制約の利用を検討する。

## 5. モジュールの追加方法

**これがこの実装の主眼。** `modules.ts` の `MODULES` 配列に1エントリ足すだけで、画面もマイク制御も共通のまま機能が増える。

```ts
export type EarModule = {
  id: ModuleId;
  name: string;
  tagline: string;
  icon: string;
  hint: (settings: EarHubSettings) => string;
  /** このモジュールが聞き取る言語 */
  recognitionLang: (settings: EarHubSettings) => LanguageCode;
  /** Claude API を使うか。使わないモジュールはキーなしでも動く */
  usesApi: boolean;
  /** 同席者の声を記録するので、開始前に断りを確認するか */
  requiresConsent: boolean;
  /** 発話が1つ確定するたびに呼ばれる */
  onUtterance: (text: string, context: ModuleContext) => Promise<UtteranceOutput | null>;
  /** 停止したときに呼ばれる。議事録の要約はここで作る */
  onSessionEnd?: (lines: string[], context: ModuleContext) => Promise<SessionResult | null>;
};
```

`UtteranceOutput` で返せるもの:

- `primary` — 画面のメイン行
- `secondary` — 補助行(翻訳モードでは原文)
- `speak` — イヤホンに返す音声(`{ text, lang }`)
- `highlight` — 強調表示

`ModuleId` に新しいIDを足し、`MODULES` に追加する。それ以外の変更は要らない。

ウォッチワードモジュールは、この土台が「翻訳と議事録の専用品」になっていないことを確かめるために入れてある。**APIを使わないモジュールが同じインターフェースのまま載ることが、プラットフォーム構造が成立している証拠。** 4つ目を足すときも、翻訳・議事録のコードには触れないこと。

## 6. API 仕様 — `POST /api/ear-hub`

### リクエスト

翻訳:

```json
{ "task": "translate", "text": "...", "from": "en", "to": "ja" }
```

要約:

```json
{ "task": "summarize", "transcript": "..." }
```

`EARHUB_ACCESS_CODE` を設定している場合、ヘッダ `x-earhub-code` が必要。

### レスポンス

成功: `{ "text": "..." }`
失敗: `{ "error": "<コード>", "message": "<日本語の説明>" }`

| status | error | 意味 |
| --- | --- | --- |
| 503 | `not_configured` | `ANTHROPIC_API_KEY` 未設定 |
| 401 | `access_code_required` | アクセスコード不一致。画面が入力欄を出す |
| 413 | `too_long` | 翻訳800字 / 要約24,000字の上限超過 |
| 429 | `rate_limited` / `budget_exceeded` | レート制限、または1日の文字数上限 |
| 422 | `refused` | モデルが応答を拒否 |
| 502 | `upstream_error` | Claude API がエラーを返した |

### ★ モデルごとのパラメータ差 — 落とし穴

`EARHUB_MODEL` で差し替えられるようにしてある以上、**モデルが受け付けないパラメータを送ると 400 で落ちる。** 送る前に判定している。

| パラメータ | 対応モデル | 判定 |
| --- | --- | --- |
| `output_config.effort` | 4.6世代以降のみ。**既定の Haiku 4.5 は非対応** | `SUPPORTS_EFFORT` |
| `fallbacks`(サーバー側フォールバック) | Opus 5 / Fable 5 系のみ | `SUPPORTS_SERVER_FALLBACK` |

実際にこれで一度事故っている。Haiku を指定した状態で `effort` を無条件に送るビルドをデプロイし、400 になった。**モデルを変えるときは `route.ts` 冒頭のこの判定を必ず確認すること。**

### 従量課金の保護

APIキーをブラウザに置けないためサーバー経由にしており、その結果このエンドポイントは誰でも叩ける。認証の代わりに支払いを守る仕組みを置いている。

- アクセスコード(`EARHUB_ACCESS_CODE`)
- IPごとに毎分40リクエスト
- 1リクエストの文字数上限(翻訳800字 / 要約24,000字)
- 1日に送る総文字数の上限(既定40万字)

**サーバーレスではインスタンスごとのメモリなので、この制限は厳密ではない。** 最終的な歯止めは Anthropic コンソール側の利用上限に置く前提で、ここはその前段の粗いフィルタ。

## 7. 環境変数とデータの置き場所

| 変数 | 既定 | 用途 |
| --- | --- | --- |
| `ANTHROPIC_API_KEY` | (必須) | 未設定なら503。ウォッチワードだけ動く |
| `EARHUB_MODEL` | `claude-haiku-4-5` | 変更時は§6のパラメータ差を確認 |
| `EARHUB_ACCESS_CODE` | 空 | 設定するとこの合言葉なしにAPIを叩けない |
| `EARHUB_DAILY_CHAR_BUDGET` | `400000` | 1日にAPIへ送る文字数の上限 |
| `NEXT_PUBLIC_GOOGLE_CLIENT_ID` | 空 | 未設定ならドライブ保存のUIが無効。voice-recorder と共用 |

`NEXT_PUBLIC_*` はビルド時に埋め込まれるので、**設定してからデプロイする**こと。あとから足す場合は再デプロイが要る。

### 保存先

既定は端末の `localStorage`。キーは `earhub.settings.v1` / `earhub.minutes.v1`(直近30件) / `earhub.code.v1`。ブラウザ単位で、サイトデータを消すと消える。**サーバーには何も置かない。**

設定で「Googleドライブにも保存する」をONにすると、議事録を止めた直後に利用者自身のドライブへ Markdown で書き出す。

- スコープは `drive.file` のみ。**アプリが作ったファイルしか読み書きできない**
- その裏返しで、既存フォルダを選ばせることはできない。保存先はアプリが作る名前付きフォルダ(既定 `hitobito Ear Hub`)
- フォルダはドライブ側で移動・改名してよい。IDで参照しているので追随する
- `drive.file` を選んだのは権限を絞るためだけでなく、`drive` や `drive.readonly` は Google の restricted scope に当たり、外部公開に第三者機関のセキュリティ審査(実費が出る)が要るため。**スコープを広げる変更は、その費用を発生させる**

## 8. ログイン機能が無い理由

会話も議事録も端末内にしか置かず、サーバーには何も保存しない。ドライブ保存も利用者自身のアカウントへ直接書くだけで、こちらを経由しない。**残すデータがサーバーにないので、本人を識別する理由がない。**

ログインが必要になるのは次を始めるとき。それまではアカウントを作らせる理由がない。

1. 議事録を「こちらのサーバー経由で」複数端末に同期する
2. 自分以外に配る(誰がいくら使ったかを分けて数える必要が出る)
3. 課金する

## 10. デプロイ

**このリポジトリの Vercel Git Integration は意図的にOFF。push してもデプロイされない。** 無料枠を不要に消費しないための判断で、回避のために再有効化しないこと。最後の `vercel[bot]` デプロイは 2026-08-24。

デプロイ経路は2つ。

1. **Vercel MCP を持つ環境から** — 現在はこれを使っている。Preview デプロイとして出し、本番ドメインと LEVEL UP 設定には触れない
2. **GitHub Actions** — `.github/workflows/vercel-preview.yml` が予備として用意してある。`workflow_dispatch` のみで、dispatch には default branch にファイルがある必要がある。`VERCEL_TOKEN` / `VERCEL_ORG_ID` / `VERCEL_PROJECT_ID` を Actions secrets に入れれば動く

Claude Code のサンドボックスからは Vercel の全ホスト(`api.vercel.com` / `mcp.vercel.com` / `vercel.com` / `*.vercel.app`)が egress ポリシーで 403 になる。トークンや CLI、MCP の追加では解決しない。詳細は `AGENTS.md` の「Deployment requests」に記録してある。

## 11. 既知の制約と落とし穴

### v1でやっていないこと

- **話者分離** — 誰の発言かは記録しない。要約プロンプトにも「話者は分離されていない」と伝えて断定させないようにしてある
- **バックグラウンド常駐** — ブラウザなので画面を開いている間だけ動く。コンセプトの「つけて会議に入るだけ」にはまだ届いていない
- **オフライン動作** — 音声認識も翻訳もオンライン前提

### 作業時の注意

- **`next-env.d.ts` は自動生成物。** `npm run dev` を実行すると参照先が `.next/dev/types/...` に書き換わる。コミットしないこと。正はビルド版(`.next/types/...`)
- **リポジトリには既存の lint エラーが24件ある**(`app/maa-iika` など)。`npm run lint` は元から失敗する。新規・変更ファイルだけを `npx eslint <path>` で確認すること
- **`app/tools/page.tsx` のポータルには未掲載。** `/voice-recorder` も同様に未掲載なので、それに倣っている。公開する判断をしたら追加する
- **`proxy.ts`(ミドルウェア)はホスト名でルーティングを分けている。** `*.vercel.app` はどの条件にも一致せず素通しになるので、Preview URL で `/ear-hub` はそのまま表示される

## 12. 次にやること

優先度順。

1. **実機確認**(§2)。ここが全ての前提。特にイヤホンのマイクで拾えるか
2. 回り込みが起きるなら、`speakSafely()` の待ち時間調整か `echoCancellation` の利用を検討
3. iOS Safari で認識が続かないなら、張り直しの間隔(`speech.ts` の `restartDelay`)を調整
4. 実用に足ると判断できたら、`app/tools/page.tsx` のポータルに掲載するか決める
5. 4つ目のモジュールを足してみる(§5)。土台が本当に汎用かの再確認になる
