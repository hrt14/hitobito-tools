# イヤホンハブアプリ『Ear OS(仮)』コンセプト

## コンセプト
いま持っているイヤホン(AirPodsでも数千円のワイヤレスイヤホンでもいい)を買い替えずに、「翻訳機」「議事録機」に変える。イヤホンは音の入出力口のままにして、認識・翻訳・要約・記録という頭脳は全部スマホ側に置く。

**イヤホンを機種変更する体験ではなく、スマホに機能を1つ追加すると、いま耳につけているイヤホンの能力が1つ増える体験にする。**

翻訳アプリでも議事録アプリでもなく、「耳の機能拡張プラットフォーム」を作る。翻訳と議事録は最初に載せる2つのモジュールであって、ゴールではない。

## セントラル(スマホ)とイヤホンの役割分担
- イヤホン: マイクで拾う/スピーカーで鳴らすだけ。専用ハードウェア不要、Bluetoothで繋がる既存イヤホンをそのまま使う。
- スマホ(セントラル): 音声認識・翻訳・要約・保存・UI表示を担う本体。バッテリーも処理能力もここに集約するので、イヤホン側の制約(電池・演算力)に機能追加が縛られない。
- この分離により「イヤホンを機能拡張する」を「スマホ側にモジュールを足す」に翻訳できる。ハードウェアを増やさずに機能だけ増える構造が核心。

## プラットフォーム構造
1つの常駐アプリの中に「聞くモード」を切り替えるモジュールが並ぶ。将来モジュールを追加してもアプリの骨格(マイク入力→処理パイプライン→出力)は変えない。

```
[イヤホンのマイク]
      ↓
[スマホ: 音声取り込み層]
      ↓
[モード選択] → 翻訳モジュール / 議事録モジュール / (将来モジュール)
      ↓
[出力層] → イヤホンへ音声再生(TTS) or 画面へ字幕・要約表示
```

- モードはホーム画面でワンタップ切り替え。同時に2つは動かさない(処理負荷・エコー干渉を避けるため)。
- 各モジュールは「音声を受け取って何かを返す」という共通インターフェースだけを守れば追加できる設計にする。

## 最初の2モジュール

### 翻訳モード(会話通訳機)
- 向かい合って話す相手の声をイヤホンのマイクで拾い、翻訳した音声をイヤホン(自分の耳)に流す。自分の発話は画面表示 or 相手のスマホ/スピーカーに戻す、の双方向会話モードを基本形にする。
- 画面には原文/訳文を字幕としても残し、聞き逃しをカバー。
- 差別化: 「スマホを相手との間に置いて画面を見せ合う」翻訳アプリの体験をやめ、自分は基本イヤホンだけ見て(画面を見なくても)会話を続けられることを目指す。

### 議事録モード(耳が記録者になる)
- 会議中つけっぱなしのイヤホンのマイクが拾った音声を、スマホ側でリアルタイム文字起こし→終了後に要約・決定事項・ToDo抽出まで自動生成。
- 話者分離(誰が発言したか)は音声の聞こえ方(左右差・音量)を手がかりにする簡易版から始め、精度は割り切る。
- 差別化: 会議アプリを別途開いて録音ボタンを押す動作をなくし、「イヤホンをつけて会議室に入る」だけで議事録が始まる状態にする。

## 技術的な検討事項(要調査・要検証)
- OSの制約: iOS/AndroidともBluetoothイヤホンのマイクをバックグラウンドで常時利用する挙動、権限、バッテリー消費は事前検証が必須。常駐前提の設計が実機で成立するかがこの企画の生死を分ける。
- エコー/回り込み: 翻訳音声をイヤホンで再生しながら同じイヤホンのマイクで次の発話を拾うため、自分の再生音がマイクに回り込まない処理(エコーキャンセル)が要る。
- オンライン依存: 実用的な精度のASR/翻訳/要約はクラウドAPI前提になりやすい。オフライン時の劣化モード(簡易オンデバイス処理 or 「今は使えません」の明示)を最初から設計に入れる。
- プライバシー: 議事録モードは同席者の発言を録る前提のため、同意取得のUI(会議開始時に一言断る導線)をモジュール仕様に組み込む。

## ロードマップ(段階)
1. 翻訳モード単体でプロトタイプ検証(1対1会話、エコー処理、体感速度)
2. 議事録モード追加、モード切り替えの土台(共通パイプライン)を検証しながら固める
3. 3つ目のモジュールを実際に追加してみて、プラットフォーム構造(モジュール追加だけで機能が増える)が本当に成立するかを検証する ← ここが企画の合格ライン

## 完了条件(この構想が機能したと言える基準)
- イヤホンを新調・ペアリング変更せずに、いま使っているイヤホンで翻訳/議事録が動く
- モードの切り替えがワンタップで、モジュール追加のたびに新しい画面体系を学び直さなくていい
- 3つ目のモジュールを追加するときに、翻訳/議事録のために書いたコードを壊さず、パイプラインへの追加だけで済む
- 翻訳モードは相手との会話中、画面を見続けなくても成立する
- 議事録モードは「会議に入ってイヤホンをつける」以外の追加操作なしで記録が始まる

# 実装(v1) — `/ear-hub`

Webアプリとして実装した。実装は `app/ear-hub/`(画面とモジュール)と `app/api/ear-hub/route.ts`(Claude API 経由)。

## 構成

```
イヤホンのマイク
  ↓  Web Speech API(ブラウザ内蔵・無料)     app/ear-hub/speech.ts
確定した発話テキスト
  ↓  モジュールの onUtterance()              app/ear-hub/modules.ts
  ↓  必要なときだけ /api/ear-hub             app/api/ear-hub/route.ts → Claude API
画面の字幕 / speechSynthesis で耳へ返す
```

モジュールは `MODULES` 配列の1エントリ。`onUtterance`(発話ごと)と `onSessionEnd`(停止時)だけを実装すれば、画面もマイク制御も共通のまま機能が増える。

## 載せた3モジュール

| モジュール | 何をするか | APIを呼ぶ回数 |
| --- | --- | --- |
| 翻訳 | 相手の発話を訳してイヤホンに読み上げる。向きはワンタップで反転 | 1発話につき1回 |
| 議事録 | 連続文字起こし。停止時に要約・決定事項・ToDo・保留事項を生成 | 停止時に1回だけ |
| ウォッチワード | 決めた語が聞こえたら耳で知らせる | 0回(端末内で完結) |

3つ目のウォッチワードは、共通の土台が「翻訳と議事録の専用品」になっていないことを確かめるために入れた。API を使わないモジュールが同じインターフェースのまま載る = ロードマップ3段目の合格判定にあたる。

## コスト設計 — 高いのは音声認識で、そこを無料にしてある

従量課金が効くのは音声認識と読み上げだが、どちらもブラウザ内蔵機能(Web Speech API / speechSynthesis)で端末側で処理する。**Claude API に渡すのはテキストだけ**なので、支払いはテキストのトークン分しか出ない。

既定は一番安い `claude-haiku-4-5`。概算(1ドル150円):

| 使い方 | トークン | `claude-haiku-4-5`(既定) | `claude-opus-5` |
| --- | --- | --- | --- |
| 翻訳の1発話 | 入力180 / 出力40 | 約0.06円 | 約0.3円 |
| 100発話の会話 | — | 約6円 | 約30円 |
| 1時間の会議をまとめる | 入力8,000 / 出力800 | 約2円 | 約9円 |

議事録は文字起こし中に一切APIを呼ばないので、会議が長くなっても課金は増えない。増えるのは停止時の1回だけ。

### モデルごとのパラメータ差

`EARHUB_MODEL` で差し替えられるようにしてある以上、モデルが受け付けないパラメータを送らないようにする必要がある。対応していないものを送るとリクエストが400で落ちる。

- `output_config.effort` — 4.6世代以降のみ。既定の Haiku 4.5 には**送らない**
- サーバー側フォールバック (`fallbacks`) — Opus 5 / Fable 5 系のみ

判定は `app/api/ear-hub/route.ts` の `SUPPORTS_EFFORT` / `SUPPORTS_SERVER_FALLBACK` にある。モデルを変えるときはここを確認する。

## ログの保存先

既定はこの端末の `localStorage`(キー `earhub.minutes.v1`、直近30件)。ブラウザ単位なので、他の端末からは見えず、サイトデータを消すと消える。**こちらのサーバーには何も置かない。**

設定で「Googleドライブにも保存する」をONにすると、議事録を止めた直後に利用者自身のドライブへ Markdown で書き出す。保存済みの記録は一覧から個別に上げ直せる。

- スコープは `drive.file` のみ。**このアプリが作ったファイルしか読み書きできず、利用者のドライブの中身は見えない**
- その制約の裏返しとして、既にあるフォルダを選ばせることはできない。保存先はアプリが作る名前付きフォルダ(既定 `hitobito Ear Hub`)で、名前は設定で変えられる
- 作られたフォルダはドライブ側で移動・改名してよい。IDで参照しているので保存先はそのまま追随する
- ファイル名は `議事録_2026-09-02_0202.md`。中身は「要約 → 区切り → 文字起こし全文」
- 保存にはこちらの費用は一切かからない。Drive API は無料で、消費するのは**利用者自身のドライブ容量**

実装は `app/ear-hub/drive.ts`。OAuth クライアントは voice-recorder と同じ `NEXT_PUBLIC_GOOGLE_CLIENT_ID` / 同じスコープを使うので、追加のGoogle設定は要らない。

## 環境変数

| 変数 | 既定 | 用途 |
| --- | --- | --- |
| `ANTHROPIC_API_KEY` | (必須) | 未設定なら503を返し、翻訳と議事録の要約が止まる(ウォッチワードは動く) |
| `EARHUB_MODEL` | `claude-haiku-4-5` | 品質を上げたいときに差し替える。上の「モデルごとのパラメータ差」を参照 |
| `EARHUB_ACCESS_CODE` | 空 | 設定するとこの合言葉なしにAPIを叩けなくなる |
| `EARHUB_DAILY_CHAR_BUDGET` | `400000` | 1日にAPIへ送る文字数の上限 |
| `NEXT_PUBLIC_GOOGLE_CLIENT_ID` | 空 | 未設定ならドライブ保存のUIが無効になる。voice-recorder と共用 |

## ログイン機能は、v1では要らない

会話も議事録も端末の `localStorage` にしか置かず、こちらのサーバーには何も保存しない。ドライブ保存も利用者自身のアカウントへ直接書くだけで、こちらを経由しない。**残すデータがサーバーにないので、本人を識別する理由がない。**

ただし「ログインは要らない」と「無防備でいい」は別。APIキーはブラウザに置けないためサーバー経由になり、その瞬間にこのエンドポイントは誰でも叩ける従量課金の入口になる。そこで認証の代わりに支払いを守る仕組みを置いた。

- `EARHUB_ACCESS_CODE` — 合言葉。1人で使うならこれで足りる
- IPごとに毎分40リクエストの上限
- 1リクエストの文字数上限(翻訳800字 / 要約24,000字)
- 1日に送る総文字数の上限

サーバーレスではインスタンスごとのメモリなので、この制限は厳密ではない。最終的な歯止めはコンソール側の利用上限に置く前提で、ここはその前段の粗いフィルタ。

ログインが本当に必要になるのは次のどれかを始めるとき。

1. 議事録を「こちらのサーバー経由で」複数端末に同期したい(サーバーに議事録を置くことになる = 持ち主の識別が要る)。ドライブ保存で済む範囲なら、同期はGoogle側のアカウントが担うので不要
2. 自分以外に配りたい(誰がいくら使ったかを分けて数える必要が出る)
3. 課金する

いずれも「サーバーにデータか請求が乗るとき」で、そこまではアカウントを作らせる理由がない。

## v1でやっていないこと

- **話者分離** — 誰の発言かは記録しない。要約プロンプトにも「話者は分離されていない」と伝えて、断定させないようにしてある
- **バックグラウンド常駐** — ブラウザなので画面を開いている間だけ動く。「つけて会議に入るだけ」に近いが、まだ画面を開く操作が要る
- **オフライン動作** — 音声認識も翻訳もオンライン前提。圏外では止まる
- **エコーキャンセル** — 読み上げ中は認識を落として `abort()` で音声を捨てる方式で回り込みを避けている。信号処理はしていない
- **iOS Safari の連続認識** — 認識が切れるたびに張り直す実装で対応しているが、実機での連続動作は未確認
